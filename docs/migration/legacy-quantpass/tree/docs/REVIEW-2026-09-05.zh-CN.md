# QuantPass 白皮书与开发清单设计评审

评审日期：2026-09-05  
结论：**需要重大修订；不批准作为正式开发基线，不批准接入真实用户资金或公开发行。允许继续需求澄清、技术验证和无真实资金的原型开发。**

## 1. 范围、证据与判定方法

本次是文档与架构设计评审，不是智能合约代码审计、渗透测试、法律意见或第三方认证。没有把文档承诺当作已经实现的安全能力，也没有把设计缺口认定为已证实的代码漏洞。没有修改白皮书、TODO、产品模型或实现代码，没有提交或推送 GitHub。

工业级不是“章节很多”或“写了需要审计”，而是需求、威胁、控制、实现、测试、发布证据能相互追踪。本次参考 [NIST SSDF v1.1](https://csrc.nist.gov/pubs/sp/800/218/final) 的安全开发生命周期思路，以及 [OWASP SCSVS](https://scs.owasp.org/SCSVS/) 的智能合约架构、经济逻辑、权限、外部依赖与安全验证分类；这不构成对这些框架的完整符合性认证。

严重程度：

- **高**：影响资金、策略保密、代币权利、业绩真实性或上线审批；必须在相关实现冻结或资金上线前关闭。
- **中**：影响兼容性、可交付性、可运营性或跨文档一致性；按所在阶段关闭，不自动阻止隔离的研究原型。

“关闭”要求有修订规范、评审记录和对应验收证据，不是把复选框改成完成。

## 2. 审批结论

| 审批用途 | 结论 | 原因 |
|---|---|---|
| 产品概念讨论 | 有条件通过 | 定位、参与者、资产与使用权分离已经清楚；仍有关键待决策事项 |
| 技术探索 / paper trading / 无真实资金原型 | 可以继续 | 应明确实验边界，不承诺生产安全或永久服务 |
| 正式开发基线、并行团队排期 | 不通过 | 关键状态与计算规则未闭合，部分不变量冲突，任务缺少可追踪验收 |
| 真实资金 Limited Mainnet Beta | 不通过 | 未提供可核验的完整安全、部署、运行与合规准入证据 |
| 公开发行及二级市场 | 不通过 | 发行权利、交易结算、持续服务和市场约束尚未定稿 |

这是对目前提供的文档证据的判断，不意味着项目不可行，也不是因为 TODO 尚有未完成任务就否决。TODO 当前有 **427 项未完成、9 项已勾选**；任务数量不代表完成度、工作量或安全成熟度，不能按勾选比例估算项目进度。

已经做对的部分：

- 将 Family、Release、Pass、Vault 和执行权限分开，避免“买到代币等于拿到用户钱包权限”。
- 将策略业绩、执行质量、容量和 Pass 市场价格分开；未启用 Pass 不应稀释策略收益。
- 已承认公开链成交会泄露行为，哈希不能独自证明实际执行，没有承诺完美保密。
- 已覆盖前端、后端、合约、运行时、数据、测试、安全、运维和合规的大部分工作域。
- Builder 的“10%”明确保留待完善，符合用户要求；本评审不擅自将其确定为 co-investment 或 bond。

## 3. 具体问题与关闭条件

### QP-REV-001｜高｜动态容量与“永不超限”不变量不闭合

证据：白皮书第 232–241 行允许 Operational Capacity 下降，第 567 行要求已绑定容量不能超过它；TODO 第 210–214 行将缩容处理留待定义。

问题：若现有已部署资本为 80，运行容量从 100 降为 50，不能靠更新一个额度数字立即消除已有仓位。若“已绑定容量”指实时重算的授权份额，形式上可以保持不等式，但不等于实际资本或风险敞口已降低。当前混用了权利额度、容量预留、实际资本和风险敞口。

要求：定义容量的单位、计价时点、净值变化影响、预留有效期及释放条件；明确缩容后的超额存量、禁止新增、按比例减仓、排队与恢复规则。不同定义分别建立不变量，不能以强制瞬时平仓隐含解决所有超额。

验收：状态规范和测试覆盖缩容、价格上涨导致超额、并发绑定、COOLDOWN 尚未结算、链重组以及扩容恢复；所有容量变动可重放核算。

建议责任角色 / 关口：协议与量化风控；容量合约实现冻结前。

### QP-REV-002｜高｜退出权与“任何故障下能完成退出”未分开

证据：白皮书第 299–304 行依赖有效 Release、预言机和未熔断状态，第 313、565、573 行承诺暂停下安全退出；TODO 第 23、192、679 行表达广泛的退出保证。

问题：撤销新增交易权限、取回闲置资产、清算持仓、跨链提回 L1 是不同操作。如果退出重用普通执行校验，Release 撤销或预言机失效可能让减仓也失败；如果全面绕过校验，又可能按恶意价格清算。停链、外部资产转账限制和无买方流动性也不是本协议能够消除的条件。

要求：逐类定义故障状态下允许的 owner 操作、权限检查、估值依据、待处理订单、结算负债与资金去向；保证“协议管理员不能主动剥夺退出权限”，但不保证外部条件下即时成交或最终到账。定义不依赖平台前端及 Keeper 的用户调用路径，说明 Gas 来源及 gas sponsor 停服后的替代方案。

验收：状态 × 操作矩阵；Release 撤销、oracle stale、Keeper 全停、前端失联、venue 故障的退出演练；明确每种情况下什么仍可做、什么必须等待。Robinhood 官方文档将 canonical bridge 的 L2→L1 提款列为带挑战期的流程；这与本地 Vault 提款应分开披露，不能混为即时退出。[官方桥接文档](https://docs.robinhood.com/chain/bridging/)

建议责任角色 / 关口：协议、安全、前端；资金路径实现冻结前。

### QP-REV-003｜高｜禁止任意转账不足以约束经济性损失

证据：白皮书第 297–305、549、564 行；TODO 第 197–205 行。已经列出单笔、敞口、滑点与频率控制，但未给出执行后的资产核对和跨笔预算语义。

问题：在允许的交易场所反复做不利交易，也可能将价值转移给交易对手，而没有一次“转到非允许地址”。逐笔滑点都合规仍可能累积消耗大量资本。单纯检查交易目标、执行前模拟或名义仓位不能证明实际余额和负债满足 Policy。

要求：定义实际资产余额变化、receiver、allowance、债务和费用的前后置条件；明确滑点独立价格基准、跨笔/跨时间窗预算、损失触发器及谁可修改阈值。异步 venue 应有待结算风险预留和成交回执核验，不可假设全部交易原子完成。说明市场正常亏损与越权风险的边界。

验收：重复小额不利交易、被操纵价格、恶意回调、异常资产行为、部分成交、超额手续费等负向用例；所有绕过路径必须回滚、停止新增风险或进入明确的待结算状态。

建议责任角色 / 关口：安全、协议、量化风控；Adapter 与 Policy Kernel 冻结前。

### QP-REV-004｜高｜TEE 从发布到链上验签的信任链没有完整定义

证据：白皮书第 169–186、319、551 行；TODO 第 260–278、292–294 行。

问题：列出 artifact hash、measurement 和 runtime key 还不够。需要说明谁验证 attestation、谁把验证结果登记为链上可接受的签名者、谁能修改 KMS 策略，以及动态加载的策略、模型和参数怎样绑定到当前 Release。合法 runtime image 本身不自动证明它加载了正确策略、正确数据或唯一的最新状态。

另一个未闭合点：Builder 本地加密后上传，但平台还要做 malware/dependency scanning。扫描发生在 Builder 本地、受信审查环境还是 enclave 内，检查结论是否可信，目前不明确。

要求：绘制可信主体与密钥权限表，覆盖 Builder、平台管理员、云账户/KMS 管理员、构建者、attestation verifier、链上 Registry 和运行时；规定 manifest 规范化、加载后哈希校验、签名 key 绑定、证书/measurement 校验、debug 拒绝、过期与撤销、数据新鲜度、状态回滚防护和并发实例隔离。明确恶意平台管理员是否在威胁模型内，以及仍然保留哪些信任。

验收：替换 artifact/模型/参数、放宽 KMS policy、伪造/过期 attestation、旧状态恢复、双实例重复出单、扫描日志泄密的红队测试和密钥访问证据。以 AWS 为候选例，其 KMS 能基于 attestation measurements 作条件检查，但这不能代替本项目的发布授权和管理员治理设计。[AWS 官方机制说明](https://docs.aws.amazon.com/enclaves/latest/user/kms.html)

建议责任角色 / 关口：安全架构、运行时、基础设施；选择生产保密方案并承诺平台不可读取策略之前。

### QP-REV-005｜高｜NAV 与绩效费缺少可执行会计规范

证据：白皮书第 359–384、426 行；TODO 第 352–374、467–473 行。

问题：`期末 NAV / 期初 NAV - 1` 只有在 NAV 已正确单位化或适当调整资金流时才有意义。若把净资产余额当 NAV，资产从 100 因入金变成 200 就会被误算为 100% 收益。当前未定义 NAV 究竟是单位净值还是总净资产，也未定义期间资金流、费用结晶、定价时点及日/周/月/年边界。

要求：编写会计规范，确定单位化净值或其他明确的资金流调整方法、gross/net fee 展示、估值源与缺价处理、固定精度及舍入、历史更正规则。定义逐 Vault high-water mark 在入金、部分提现、清仓、重新启用和迁移时如何调整；净值、费用应计与领取不得重复扣款。不活跃 Pass 不计零收益的原则保留，不需要改回持有人平均收益。

验收：黄金样例至少覆盖纯入金不产生收益、纯提现不产生亏损、先亏后赚、带资金流的 HWM、跨时区边界、费用未领取、资产事件、缺价和重组；独立计算器与账本逐笔对账。

建议责任角色 / 关口：量化、账务、协议；Performance/Fee 规范冻结及对外展示业绩前。

### QP-REV-006｜高｜Reference Vault 不自动证明普通用户能获得同等策略执行

证据：白皮书第 219–221、359–396、554 行；TODO 第 358、475–482 行。

问题：Reference Vault 连续、历史不可重置，只解决部分真实性问题。同一 Release 仍可能按输入、账户标签、资金规模或调度顺序产生不同结果；参考账户可能优先成交，消费者承担剩余流动性。历史 commitment 可防止事后改写，却不保证写入的记录完整或原始记录真实。

要求：定义 Reference 的资金、最小规模、实际费用、输入和 Policy；解释它与不同用户约束的可比范围。制定调度/分配公平性规则、可审计的决策批次和输入版本关联，在不公开策略机密的条件下保留核验证据。允许差异化策略时，应诚实披露参考收益不是可直接复制的收益承诺。

验收：完整成交与费用可独立重建曲线；检测参考账户专享价格、漏单、选择性失败记录和版本切换。执行质量 cohort 应按“期间曾启用”取样，不能因期末已退出而删除亏损用户；TODO 的“排除非活跃 Vault”需澄清此边界。

建议责任角色 / 关口：量化、数据、安全；业绩公开和市场宣传前。

### QP-REV-007｜高｜授权撤销、再绑定和部分成交的跨状态语义不足

证据：白皮书第 245–256、275–305、568 行；TODO 第 89–95、180、200、206、284–288 行。

问题：唯一 nonce 防重复执行，不必然防止一个从未执行的旧 Intent 在撤销后重新绑定相同 Pass/Policy 时重新变得有效。授权版本、执行 key 轮换、未成交订单与容量释放之间还没有明确关系。部分成交后消耗整条 nonce 或允许重试，分别可能导致遗漏余量或重复下单，必须按实际 venue 模型设计。

要求：规定授权 generation/epoch 或等价失效机制；Policy hash 不能独自表达“同样规则的新一次授权”。定义订单累计成交上限、预留额度、取消确认、终态及链重组恢复。COOLDOWN 在负债和待成交订单未结清前不得释放给下一持有人。

验收：bind→签名→revoke→同策略 rebind→旧 Intent 提交；转让、key 轮换、并发 Keeper、部分成交重试、取消与成交竞态、重组恢复等测试全部有预期状态。

建议责任角色 / 关口：协议、执行后端；状态机与签名 schema 冻结前。

### QP-REV-008｜高｜全局管理权限可能绕过用户批准的版本边界

证据：白皮书第 309、537–543 行；TODO 第 169、193、198 行。

问题：“Vault 尽量不可升级”和“Adapter 变更有 timelock”不是严格权限保证。若用户只批准一个可变 Registry 条目或代理地址，管理员可能替换其背后实现、资产列表、oracle 或风险参数，而无需用户重新授权。Timelock 提供反应时间，不等于用户同意。

要求：明确不可变部分、升级主体、多签阈值、时锁、可撤销窗口，以及 emergency role 的单向权限；用户授权应绑定具体配置版本/实现约束，或明确授权了哪些有限变更。外部 venue 自身升级也应进入暂停和再验证流程。禁止利用“修复”绕过费用上限或扩大资产权限。

验收：角色与操作权限矩阵；管理员恶意更新和被盗 key 的测试；证明全局配置改变不能静默扩大旧授权，或清楚披露并由用户接受该信任边界。

建议责任角色 / 关口：协议、安全、治理；权限架构冻结前。

### QP-REV-009｜高｜发行与二级交易还没有完整的资产结算设计

证据：白皮书第 227、245–256、422 行；TODO 第 175–182、405–406、648–651 行。

问题：当前有 primary sale / royalty 接口和市场前后端任务，但尚不足以定义发行、购买与二级交易的资金闭环。缺少选定的结算模式、支付与 Pass 转移原子性、失效订单、撤单、退款、部分成交及费用分配规则。ERC-20 可互换份额与独立 Pass 状态也需要明确的锁定或托管模型。

要求：选择首版市场模式并写明自建/复用边界、发行失败条件与退款路径、绑定和卖出竞态、市场 fee cap、royalty 执行范围、用户拒绝成交/交易失败时的处理。市场运营方和做市商需有数据访问、优先级和关联账户交易规则，不只是收入分开披露。

验收：从支付到权利到账的端到端账务守恒；重复购买、绑定后旧卖单、支付失败、token receiver 回调、取消竞态和链重组测试。若采用 ERC-2981，应明确它提供 royalty 信息而非强制所有市场付款，不能把接口支持计为版税已可靠收取。[ERC-2981](https://eips.ethereum.org/EIPS/eip-2981)

建议责任角色 / 关口：产品、协议、市场后端；发行合约冻结及市场测试网验收前。无市场的运行原型可先行。

### QP-REV-010｜中｜EIP-712 domain 任务表述不符合标准字段边界

证据：TODO 第 103 行要求在 domain 中绑定 `Vault`、`nonce` 和 `deadline`。

问题与要求：EIP-712 的标准 domain 字段为 `name`、`version`、`chainId`、`verifyingContract`、`salt` 的适用子集，不应自行添加上述私有 domain 字段。Vault、nonce、deadline 应绑定在 typed message 中；若 Vault 本身是验证合约，可同时由 verifyingContract 指定。nonce 的消耗仍由协议实现，签名编码标准不自带防重放。[EIP-712 标准](https://eips.ethereum.org/EIPS/eip-712)

验收：固定 JSON/Solidity/SDK 测试向量、钱包显示与签名恢复一致；修改任何关键字段后验签或业务校验失败，兼容 EOA 与 ERC-1271。

建议责任角色 / 关口：协议、SDK、前端；签名接口冻结前。

### QP-REV-011｜中｜固定供应、持续服务与待定承诺尚未形成一致权利契约

证据：白皮书第 11、227、448–460 行；TODO 第 47–49、61–77 行。

问题：“固定数量”与“市场授权后可增发”的例外未确定具体权利主体和程序；永久 Family 身份不应被理解为无条件永久运行服务。Builder 失联、云成本上升、策略停服后，持有人的剩余权利与退出补偿未定义。

要求：区分永久身份、使用许可期限、版本访问权、容量动态变化和服务可用性义务；列出运行成本与谁支付、停服/退市/废弃流程。给“10%”及 Reference 资本来源等待决策项指定责任角色和最迟决定关口。在决定前，不把它们写成既定 tokenomics，也不以保证金名义暗示亏损赔付。

验收：代币条款、白皮书和合约约束逐条对应；模拟 Builder 消失、运行停止及容量长期归零；公开发行前所有影响购买权利的待决策项关闭。

建议责任角色 / 关口：产品、经济设计、法律；定价与发行审批前。

### QP-REV-012｜中｜Robinhood 优先尚未转化为可部署的依赖证据

证据：白皮书第 464–499、624 行；TODO 第 53–56、554、633–646 行。

问题：选定 Robinhood Chain 和链参数不等于选定实际交易场所、可交易资产、价格源、接入资格与结算模型。mock Adapter 的演示不能验证真实 liquidity、权限或故障退出。首版 spot 是文档建议，不应冒充用户已确定的需求。

要求：建立依赖登记表：资产/venue、网络、合约地址、版本与升级权限、oracle、市场时段、用户地域/转让限制、最小交易单位、最终性、故障恢复、官方来源和核验日期。测试网与主网分别记录；证据不足标为阻塞而不是自动回退 BSC 或改成另一资产类型。

验收：一个实际候选 venue 的接入验证与故障实验、资产与资格边界、RPC/finality 行为记录；由产品负责人确认首版资产类别。本次核对官方链资料，不声称已经测试 RPC、资产合约或主网流动性。

建议责任角色 / 关口：集成、产品、合规；真实 Adapter 选型及承诺首版交付范围前。

### QP-REV-013｜中｜TODO 是工作域清单，不是可审批的交付计划

证据：TODO 各 P0–P12 章节、第 158、621、664–681 行。已有模块级完成标准，但大部分条目没有独立编号、具体责任人、依赖、工作量或验收证据链接。

问题：P0–P12 实际混合领域与阶段，不能直接当严重程度或执行顺序。427 个未完成复选框颗粒度差异很大，“编写状态机”和“完成审计”无法以同一任务单位估时；“用户永远不会误解”等表述也不可直接测试。

要求：保留总清单，将首版关键路径拆成带稳定 ID 的工作项。每项至少含需求/风险来源、输入与输出、负责人和审核人、依赖、估算范围、验收条件、证据链接、目标关口、状态。未来扩展工作可暂不精排。不要为了完整性强行先建全部微服务。

验收：任一白皮书安全承诺都能追踪到设计、实现任务、负向测试和审批证据；选取“买 Pass→入金→运行→停止→出售”路径，能追踪全部跨团队依赖。前端可用性采用具体场景、失败率/理解度目标和用户测试，不采用绝对心理保证。

建议责任角色 / 关口：技术负责人、产品、项目管理；正式排期和多人并行实现前。

### QP-REV-014｜高｜测试网、保密运行、市场与法律的上线关口未同步

证据：白皮书第 587–605 行；TODO 第 561、633–651、666–681 行。

问题：白皮书将生产保密运行放在 Phase 2，但 TODO 的 Beta 验收未显式要求这条链路及其证据；前阶段采用 mock/paper 或受限 Pass，也不能验证后续真实市场的转让与绑定竞态。TODO 将正式法律意见写在“主网公开销售前”，但更早接入真实消费者资金是否需要审批尚未形成明确关口。

要求：定义独立发布包：无资金原型、真实 Adapter 测试网、保密运行测试网、受限资金 Beta、发行与市场。每次发布写明必须具备的控制和证据，新增市场/升级能力要重新经过对应测试与审计范围，不能沿用旧组件审计作为整个系统已审计。真实资金 Beta 前按实际司法辖区和业务活动完成适用性评估，由合格法律人员确认准入条件；这里不预判具体法律分类。

验收：发布 readiness 表列出版本、部署地址/构建摘要、审核人、测试与审计报告、未关闭风险、cap、监控、停服/退出方案和签字记录。任何关口未满足只能进入更低风险环境；不得通过“allowlisted 小额”自动豁免资金安全和法律评估。

建议责任角色 / 关口：发布负责人、安全、法律；任何真实资金发布前，并在新增能力时复审。

### QP-REV-015｜中｜缺少可量测的性能、成本和恢复目标

证据：TODO 第 567–589、621 行。已有 SLO、备份和演练任务，但未提供目标及容量模型。

问题：策略扇出至大量独立 Vault 后，TEE、数据、RPC、Gas 和 Keeper 的时延与成本会影响可用性及实际收益。没有规模和时延预算，就不能判断架构能否支撑产品承诺；“有备份”不等于可恢复运行和正确账本。

要求：由产品和技术共同确认支持的活跃策略/Vault 数、决策频率、峰值扇出、可接受 Intent 年龄、执行延迟分位数、Gas/用户成本、可用性、RTO/RPO 及报警到响应目标。分别规定链上事实、重建索引、保密策略状态和密钥的恢复办法。明确拥堵时限流、公平排队、欠费和停止新增风险的行为。

验收：压测与费用预算、故障注入、从备份恢复并与链上资产/费用/容量对账的报告；指标由业务确认，不在本评审中编造通用“工业级数字”。

建议责任角色 / 关口：SRE、执行后端、产品；生产架构与 Beta readiness 前。

### QP-REV-016｜中｜关联文档的定位、公开性与保证范围仍有歧义

证据：README 第 42 行否认 strategy token launchpad；旧安全模型第 109–114 行把持仓和订单列为 never on-chain，而白皮书第 333 行说明公开链暴露成交；TODO 第 685–687 行同时引用新旧文档。白皮书第 637 行对容量超卖的表述也需要限定作用域。

问题：新白皮书的方向比旧模型明确，但没有正式的优先级/废弃标记。团队可能继续按旧 CEX 隐私假设实现新链上产品。固定供应能约束注册在本协议中的容量分配，不能证明 Builder 没有在其他平台出售同一策略，或通过另一个身份发布近似策略。

要求：确定唯一规范源，其他文档标记实验性、被替代部分及适用范围；统一“量化策略代币发布以及运行平台”的定义。分别陈述链上强制保证、TEE/管理员信任假设、统计估计、合同约束和无法保证的事项；容量独占与反克隆不得写成无需外部信任即可证明。

验收：术语与承诺对照表通过交叉审阅；无相互矛盾的强制要求。文档 CI 检查失效链接/版本引用，关键安全承诺变更需要审核。

建议责任角色 / 关口：技术写作、产品、安全；下一版白皮书发布及开发基线审批前。
