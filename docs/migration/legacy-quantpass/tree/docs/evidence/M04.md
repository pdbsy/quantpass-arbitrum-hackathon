## 必须影响后续设计的证据

1. Robinhood 将链描述为 permissionless，Stock Token 则有单独的发行与地区限制。因此“能调用链”不能作为 QuantPass 发行、分销、自动执行或收费均合规的证明。本报告不是法律意见；主体、服务地区和法律评估仍待确认。[链说明](https://docs.robinhood.com/chain/)、[Stock Token 披露](https://docs.robinhood.com/chain/stock-tokens/)
2. Stock Token 提供标的证券经济敞口，不给出对标的发行人的股东权利；不能在页面把它等同于直接持有美股。首版仍仅讨论用户指定的美股敞口资产，不自动加入 ETF、杠杆或借贷。[官方产品定义](https://docs.robinhood.com/chain/stock-tokens/)
3. Token 原始余额和公司行动 multiplier 分离。链上 feed 已含 multiplier，REST 报价是未调整的标的 bid/ask；混用会重复调整或漏计。必须在统一估值口径、公司行动事件与对账中测试，不能把余额变化直接当收益。[接口说明](https://docs.robinhood.com/chain/stock-token-apis/)、[集成说明](https://docs.robinhood.com/chain/building-with-stock-tokens/)
4. 价格 feed 需要独立核验代理地址、精度、时效、sequencer 恢复等待期与 oraclePaused；暂停不是价格等于零。不能把文档中的示例 require 当作完整工业级风险控制。[预言机说明](https://docs.robinhood.com/chain/oracles-and-price-feeds/)
5. 软确认、提交 L1、L1 最终性不同。存款、成交、提款和不可逆服务结算须定义各自确认门槛、重组回退和幂等键；官方公共 RPC 不能当生产 SLA。[最终性](https://docs.robinhood.com/chain/transaction-finality/)、[公共端点限制](https://docs.robinhood.com/chain/connecting/)
6. 官方列出 RFQ、AMM 等候选路径，不等于 QuantPass 已批准具体 router/pool/spender 或保证流动性。直接向发行人 mint/burn 需要获准参与者资格；不能把平台角色“做市商”的商业描述当作已经获得该资格。[交易路径说明](https://docs.robinhood.com/chain/building-with-stock-tokens/)

## 保密威胁与权限表（候选要求，不是已实现）

| 主体 | 合理权限 | 必须防止 / 残余风险 |
|---|---|---|
| Builder | 创建策略与发布承诺，按确认规则付租 | 固定代码也可能预埋按时间/行情触发的不利成交；hash 不证明经济行为诚实 |
| Consumer | 自己的资金授权、停用、提款 | 不因购买 Pass 获得源码；但公开链上的成交、仓位与时间仍可被推断分析 |
| 平台管理员 | 调度、账单、公开状态 | 不应默认读明文/修改策略；若同时能改密钥释放政策，就不能承诺管理员不可见 |
| 云/宿主管理员 | 宿主运维 | 宿主与 enclave 边界有助隔离；普通 CVM 的 guest OS/guest root 在可信计算基内，不能混淆为被隔离的宿主管理员 |
| 执行方 / venue | 必要交易意图、有限授权 | 不得获得提款权或策略明文；仍可从意图推测策略，不允许任意目标地址/任意 calldata |
| 接续运营者 | 经竞价取得的运营责任与后续分成 | 源码权限仍待 D4；转移运营权不自动释放解密密钥，也不改策略和消费者费用 |

密钥必须分离：用户钱包签名密钥不进入策略；Builder 发布密钥用于承诺；artifact 内容密钥只在批准环境解密；runtime 短期签名密钥只签受限意图；备份密钥与回放防护保护状态；密钥释放政策管理权限本身也是信任边界。平台 root 持有所有权限的单机“加密”不满足管理员不可见目标。

## 候选保密路线与验证清单

- Nitro Enclave 作为候选：AWS 文档支持把密钥操作绑定到 attestation measurement。EIF 包含未加密的代码/数据，因此敏感策略不能直接明文打进公开/宿主可读镜像；候选是固定 loader + 加密策略包 + 内容承诺核验。Debug 的零 PCR 不能加入正式允许集合。[AWS KMS 与证明](https://docs.aws.amazon.com/enclaves/latest/user/kms.html)、[镜像与秘密](https://docs.aws.amazon.com/enclaves/latest/user/connect-enclave-kms.html)、[Debug 说明](https://docs.aws.amazon.com/enclaves/latest/user/getting-started.html)
- Confidential VM 作为对照：兼容性和迁移可能更直接，但可信计算基包含 guest OS。若平台自己管理 guest root，仍需约束 guest 内的代码/策略访问，不能只凭“用了机密 VM”就保证平台看不到。[Microsoft TCB](https://learn.microsoft.com/en-us/azure/confidential-computing/trusted-compute-base)
- 硬件验收必须覆盖：可信根/签名、nonce 与时效、measurement、debug、版本与回滚、包 digest、签名公钥绑定、密钥只释放给被证明的接收者、受限输出、崩溃恢复和旧状态重放。错任何一项拒绝放钥，不能降级到明文执行。仅本地自签名 fixture 不作为 TEE 验收。
- 未建立资源、未运行硬件实验、未测启动/推理时延、无月租报价。成本模型所需输入：地区/实例计费、CPU/内存/模型大小、每策略频率与并发、冷/热启动、储存/带宽、KMS/证明请求、RPC/行情、恢复和备用资源。没有这些输入不承诺“便宜且永久可运行”。
