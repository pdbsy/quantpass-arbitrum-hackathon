# AlphaForge Qinfra stage 2: language-independent quantitative strategy interface

Scope confirmed by user: no existing strategy, no language preference, quantitative strategy integration only. First merge and validate Qinfra stage 1, then implement stage 2 locally/mock. No live market endpoint, execution, credentials, code upload/eval, subprocess strategy runner, or arbitrary webhook.

Proposed deliverables:
1. Versioned JSON strategy context and target-weight decision envelope, with a documented HTTP protocol reusable from any language. Context exposes only observed quotes/current positions/cash/limits, never future fixtures. Decision binds run ID, observed frame, expected revision, command ID and protocol version. Exact integer cash/quantity strings; target BPS total <=10000; eligible assets fixed at creation. Missing target is zero; no shorting/leverage.
2. Built-in rebalance and external-target modes use a shared target execution path. External runs stay in cash until a valid decision, and risk monitoring always proceeds independently. Reject stale, future, duplicate-conflicting, paused or stopped decisions without trading; replay identical request idempotently. Stop retains precedence and cannot be overridden by an external controller.
3. Authenticated owner-scoped context/decision endpoints, strict schemas and bounded bodies; existing local session/origin protections retained. Provide executable Node reference client (existing pinned runtime), protocol examples usable from Python without installing a new runtime.
4. Multi-asset RWA-A/RWA-B UI configuration and price-trigger asset selection; percentage triggers remain whole-portfolio. UI selects internal/external strategy, displays protocol/run endpoint, last accepted decision/frame and waiting/paused/stopped/error state. Full implementation/version/time provenance in records.
5. Persistence/recovery and liveness checks with meaningful regression tests: external decision does not leak across owner/run, transaction rollback, retries after restart, stale snapshots, concurrent stop, contribution/revision changes, partial liquidity, and stale strategy input. Preserve v1 persisted runs and synthetic dataset hashes.
6. Quantitative acceptance and complete local/CI checks with C/R/S and identity metadata. Source retained independently from stage one. Stage-two merge is not implied by the specific stage-one merge instruction.

Storage/performance investigation: stage-one finite replay has 120 frames, run commands capped at1000 and in-state history<=2000; Vault explicitly requires events/receipts count==revision and caps history at9999. Sustained replay must not just remove these safety bounds or silently drop audit history. Implement time-window continuation separately only with durable journal/checkpoint compatibility verified. Protocol/context/monitoring can land without claiming unlimited production runtime.
